# 超越轮次制 Agent

标准的 Agent harness 已经展现出了惊人的生产力：给语言模型一组工具，记录工具返回的结果，然后不断重复，直到任务完成。对于编程和网页任务，这个抽象往往恰到好处。

但当环境拥有自己的节奏时，它就开始显得不那么自然了。

机器人、语音界面或协作型 Agent 并不总能等模型完成一个漫长的轮次。推理期间，传感器状态会发生变化；人会中途打断；有些事件如果不能及时处理，很快便会失效。环境并不是一个会礼貌地等待每次模型行动结束、再返回结果的函数。

## Harness 能解决什么

一个可靠的 runtime 应当承担很多工作：

- 调度工具并管理并发；
- 过滤嘈杂的观测；
- 执行严格的安全约束；
- 缓存稳定状态，并为紧急事件选择正确的处理路径；
- 控制预算，并从失败中恢复。

这些都是系统层面的责任。如果把它们塞进模型权重里，系统只会更难验证，也更低效。

## 模型从哪里开始介入

当 Agent 需要结合尚未完成的推理去理解一次打断时，边界就发生了变化。

假设模型正在规划一个多步骤操作，而一条新观测推翻了早期的某个假设。Runtime 可以停止生成并追加这个事件，但模型仍然必须判断：哪些 belief 依然成立，计划的哪一部分需要修改，以及这个事件到底是否相关。

这已经不只是消息路由，而是在异步证据下更新状态。

## 从轮次走向事件

一个事件驱动的 Agent，可以用四种面向模型的基本原语来描述：

1. **观测事件**：携带来源和时间元数据；
2. **belief 更新**：让状态修订成为显式操作；
3. **动作**：发送给工具、控制器或人的指令；
4. **yield 策略**：决定何时等待、恢复，或请求下一次观测。

这种表示不必模仿人类认知。它只需要保留下游策略所依赖的因果和时间差异。

## 一个有用的研究分界

最有价值的问题，并不是抽象地争论“模型还是 harness”，而是：当 runtime 已经提供了干净的事件、可靠的时钟和可执行的约束之后，还剩下哪些失败？

如果剩下的是调度问题，就修 runtime；如果是 belief 更新、时间 credit assignment，或判断“不完整的推理是否已经足够支持行动”，那就可能需要模型侧的学习。

这样的分界，能把一场哲学争论变成一套可以实验验证的研究计划。
