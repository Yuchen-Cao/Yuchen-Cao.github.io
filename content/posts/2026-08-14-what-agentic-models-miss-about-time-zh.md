# Agentic 模型仍然不懂的时间

语言模型极其擅长处理序列，但序列中的位置并不等同于时间。

一千个 token 可以在几秒内生成，也可能分散在几分钟里。模型推理时，环境可能一直保持不变，也可能恰好在两个相邻 token 之间突然改变。一旦 Agent 开始与工具、传感器或人交互，我们熟悉的 token index 就不再是一个可靠的时钟。

这种错位很容易被 Benchmark 隐藏起来。大多数 Agent 评测都会把世界串行化成一个循环：

1. 提供一次观测；
2. 让模型完成一个轮次；
3. 执行一个动作；
4. 返回下一次观测。

这个循环很方便，却暗中假设模型思考期间不会发生任何重要的事情。在真实系统中，这个假设经常是错的。

## 三种不同的时间

我们需要把通常混在一起的三个量分开：

- **token 位置**——一个 token 在模型序列中的位置；
- **交互步数**——Agent 当前处于第几次观测—动作循环；
- **真实时间**——一个事件实际发生的时刻。

在简单任务里，三者彼此相关；到了实时环境中，它们却可能截然不同。一个有用的时间表示应当保留这些差异，而不是让 harness 把所有时间信息都翻译成自然语言。

## 为什么文本里的时间戳还不够

最简单的方案，是在每次观测后追加类似 `[已过去 12.4 秒]` 的文本。这是一个很有价值的 baseline：它不需要修改架构，也可以直接利用模型已有的能力。

但文本时间戳同样有代价。它消耗上下文，把时间与格式纠缠在一起，而且只有 runtime 决定输出 token 时才会出现。更重要的是，它把交互中一个连续变化的属性，变成了偶尔出现的语言提示。

显式的时间通道提供了另一种 inductive bias。Token 可以保留原本的位置编码，同时获得关于事件时间、来源或有效期的额外元数据。这样，模型就能同时对序列顺序和真实流逝时间进行推理，而不必把二者当成同一件事。

## 真正的训练问题是行为

给模型加上时钟，并不会自动带来时间能力。模型仍然需要经历那些会让时间真正影响决策的任务。

设想一个答案只有在目标时间窗口内给出才算正确的任务。如果模型答得太早，单一的成功奖励只能说明这条 trajectory 失败了，却不会告诉模型：它应该等待、检查时钟，还是更快地完成推理。当模型从未学会一种有效的等待行为时，稀疏奖励会让探索问题尤其严重。

这提示我们可以设计一套 curriculum：

1. 通过示范或受约束的 rollout，先建立有效的时间相关动作；
2. 使用“过早、准时、过晚”等更密集的区别来训练；
3. 逐步扩大动作空间，并减少 scaffolding；
4. 在不同解码速度和环境延迟下评测。

关键测试并不是模型能不能读懂一个时间戳，而是当 token 数量、计算时间和事件时间被刻意解耦之后，学到的策略是否仍然校准良好。

## 不只是一个更好的时钟

时间感知最终会改变交互协议本身。一个模型即使能够表示时间，如果它仍然只能在完整轮次之间接收观测，就依旧无法在漫长思考的中途做出反应。

因此，更深层的方向是事件驱动：世界变化时观测随之抵达；安全关键信号能够打断正在进行的推理；Agent 在不同时间尺度的事件之间持续维护自己的 belief state。

时钟不是完整的解决方案。它只是第一块基础设施——让那个一直缺失的问题终于显现出来。
